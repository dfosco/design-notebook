# 0.10.0-first-look candidate

This document describes the first-look package candidate. It is not a notice that the package has been published.

## Included workflow

The package provides a file-first notebook format for prototypes, canvases, MDX documents and existing Sites. The read-only client can run locally with `design-notebook dev <notebook-root>`. Build a portable static review with `design-notebook build <notebook-root> --out-dir dist --base /`. For a hosting prefix, replace `/` with the root-relative path that will contain the site, such as `/design-review/`.

The build emits the notebook viewer, canonical shell pages for `/canvas/<id>`, `/docs/<id>`, `/sites/<id>` and `/<prototype-id>` plus authored prototype views, runnable prototype routes, canvas snapshots, compiled documents and referenced assets. Site views use `?view=<view-id>`. The public shell page and the embedded runnable prototype path are separate. It does not upload or deploy the output. A preview can use any static file server after the dev process has stopped:

```sh
cd dist
python3 -m http.server 4173
```

See the [publishing guide](../format/publishing.md) for root and subpath hosting, direct-route refresh behavior and a GitHub Pages recipe.

In the source checkout, the canonical fixture is `examples/first-look/notebook/`. Create a separate ignored working copy at the repository root, then start the client from that notebook folder:

```sh
npm run example:init
cd example-notebook
npm run dev
```

The example folder's `dev` script resolves the Design Notebook package above it and uses the current source checkout. It treats the example folder as notebook content, not the repository root.

## First-look limits

The notebook format is file-first. In this source candidate, geometry-only local move/resize saving through the server is still pending integration verification. The agreed local behavior appends existing JSONL geometry events and does not use browser storage. Until that check passes, edit placement geometry directly in JSONL. Static output has no writable local service, and there is no general notebook mutation API or mutation CLI. Prototype builds use the core-selected Statefully runtime. Existing applications represented as Sites remain externally owned; local Site source and development URLs are not included in static output. Unsupported required content is reported as unavailable rather than silently accepted. See the [authoring guide](../authoring.md) and the [included example](../../examples/first-look/notebook/).

The project selected MIT for the package. The current package candidate includes a root `LICENSE` file and `MIT` package metadata; the earlier `UNLICENSED` tarball is not covered by that decision. The separate Tiny Canvas MIT notice remains included. This package is unpublished and clean-consumer qualification is still pending. Do not publish this candidate until qualification passes and publication is explicitly authorized.

## Candidate checks before release

Before publishing, review the exact package file list and dependency audit, verify the root MIT license and separate Tiny Canvas notice, then build a tarball and install it into a clean consumer using the supported Node range. Run the packaged CLI against the included example, review root and prefixed static output, and verify direct URLs after serving the output independently.

After those checks and explicit release authorization, create and publish the reviewed tarball:

```sh
npm pack
npm publish ./design-notebook-0.10.0-first-look.tgz
```

Do not publish from an unreviewed working tree. For a static deployment, build with the destination path and upload the **contents** of the output folder to that path, preserving generated subdirectories. For example, a project mounted at `/design-review/` uses:

```sh
npm run build -- ./notebook --out-dir dist --base /design-review/
```

Upload `dist/` contents to the host's `/design-review/` document root and preserve generated route directories. Static hosts need to serve directory `index.html` files for direct canonical route requests. Deployment is a separate action and requires explicit authorization.
